Invoicing, payment capture, and refunds for B2B billing.

The Ledger API is a resource-oriented HTTP API for issuing invoices, capturing payments against them, and refunding captured funds.

Conventions

  • Transport. HTTPS only. Requests over HTTP are rejected at the edge; no redirect is issued, because redirecting a request that carries a credential would leak that credential to the plaintext hop.
  • Encoding. Request and response bodies are UTF-8 encoded JSON.
  • Time. All timestamps are RFC 3339 date-time values in UTC with a Z offset (for example, 2026-09-01T14:32:07Z).
  • Money. All monetary values are represented by a Money object holding an integer amount in the currency's minor unit and an ISO 4217 currency code. See the Money schema for the zero-decimal and three-decimal currency rules.
  • Identifiers. Resource identifiers are opaque, prefixed strings (inv_, pay_, ref_, cus_). Do not parse them, infer ordering from them, or assume a fixed length beyond the documented maximum.

Versioning

The major version is pinned in the path (/v1). Backward-incompatible changes ship as a new dated release, which an integration opts into with the Ledger-Version header. Omitting the header pins the request to the release that was current when the account's first API call was made, so an unmaintained integration never breaks silently.

Adding an optional request field, adding a response field, or adding a new enum member to a response is not treated as breaking. Clients must ignore unrecognized response fields and must tolerate unrecognized enum members rather than failing closed.

Errors

Errors use application/problem+json as defined in RFC 9457. A declined payment is not an HTTP error; see the Payment schema.

Invoices

An invoice is a request for payment. It moves through an explicit state machine: draft -> open -> paid | void | uncollectible. Only a draft invoice is mutable.

Create a draft invoice

Creates an invoice in the draft state. A draft invoice is not visible to the customer, accrues no dunning, and can be edited or deleted. Call finalizeInvoice to issue it.

This operation is not idempotent by HTTP method, so an Idempotency-Key header is required. See the header description for replay and conflict semantics.

Authorizations:
secretKey
header Parameters
Ledger-Version
string <date>
Example: 2026-09-01

Pins the request to a dated API release, for example 2026-09-01. Omit to use the release pinned to the account. Pin explicitly in any integration you intend to maintain.

Idempotency-Key
required
string [ 16 .. 255 ] characters
Example: 8f14e45f-ea1b-4c2d-9a35-7b1d6e0c3a92

A client-generated unique key that makes this POST safe to retry. Use a UUIDv4 or another value with at least 128 bits of entropy, and generate it once per logical operation, not once per HTTP attempt.

Semantics:

  • First use. The request is processed and the response is stored against the key for 24 hours.
  • Replay with an identical body. The stored response is returned verbatim, with the original status code and an Idempotent-Replay: true header. No new resource is created.
  • Replay while the original is still in flight. 409 with the idempotency_in_progress error code. Retry after a short delay.
  • Reuse with a different body. 409 with idempotency_key_reused. Nothing is processed. This is a bug in the caller: the same key is being used for two different operations.
  • After 24 hours. The key is forgotten and a request bearing it is treated as new. An integration that retries on a schedule longer than 24 hours must not rely on this header for deduplication.

The key is scoped to the account and the endpoint. The same key may be used on createInvoice and on createPayment without collision.

Finalize a draft invoice

Transitions an invoice from draft to open, freezing its line items and assigning a sequential, gapless invoice_number for the account's current financial year.

Finalizing is the point at which the invoice becomes a legal document in most jurisdictions. After this call the line items cannot be edited; correct a finalized invoice by voiding it and issuing a new one, or by issuing a credit note.

This operation is effectively idempotent by state: calling it on an invoice that is already open returns 200 with the unchanged invoice rather than an error. Calling it on a paid, void, or uncollectible invoice returns 422.

Void an open invoice

Transitions an open invoice to void. A voided invoice is cancelled and will not be collected, but it is never deleted and its invoice_number is never reused, because reusing or removing a number would break the gapless sequence that auditors rely on.

An invoice with any succeeded payment against it cannot be voided; refund the payments first. That attempt returns 422 with invoice_has_payments.

Create a payment against an invoice

Attempts to capture funds against an open invoice.

A declined payment is a 201, not a 4xx. The HTTP status describes whether the API understood and accepted your request; it does not describe the commercial outcome of the attempt. A card decline, an insufficient-funds response, or a bank rejection all produce a Payment resource in the failed state with failure_code and failure_message populated. Branch on status, never on the status code, to decide what to tell the payer.

Some payment methods settle asynchronously. Those return a payment in the processing state; the terminal outcome arrives on the payment.succeeded or payment.failed webhook. Do not poll.

Idempotency-Key
required
string [ 16 .. 255 ] characters
Example: 8f14e45f-ea1b-4c2d-9a35-7b1d6e0c3a92

A client-generated unique key that makes this POST safe to retry. Use a UUIDv4 or another value with at least 128 bits of entropy, and generate it once per logical operation, not once per HTTP attempt.

Semantics:

  • First use. The request is processed and the response is stored against the key for 24 hours.
  • Replay with an identical body. The stored response is returned verbatim, with the original status code and an Idempotent-Replay: true header. No new resource is created.
  • Replay while the original is still in flight. 409 with the idempotency_in_progress error code. Retry after a short delay.
  • Reuse with a different body. 409 with idempotency_key_reused. Nothing is processed. This is a bug in the caller: the same key is being used for two different operations.
  • After 24 hours. The key is forgotten and a request bearing it is treated as new. An integration that retries on a schedule longer than 24 hours must not rely on this header for deduplication.

The key is scoped to the account and the endpoint. The same key may be used on createInvoice and on createPayment without collision.

object (Money)

A monetary value.

amount is an integer in the minor unit of currency, never a decimal. Floating-point types cannot represent every decimal fraction exactly, so accumulating them across a ledger drifts; integers do not.

The minor unit depends on the currency, and there is no safe default:

  • Two-decimal currencies (INR, USD, EUR): amount is paise, cents, or cents. 450000 INR is Rs 4,500.00.
  • Zero-decimal currencies (JPY, KRW, VND): amount is the whole unit. 4500 JPY is Yen 4,500.
  • Three-decimal currencies (KWD, BHD, TND): amount is thousandths. 4500 KWD is KD 4.500.

Do not hardcode a divisor of 100 when formatting for display.

Refunds

A refund returns captured funds to the payer. Refunds are only valid against a payment in the succeeded state.

Refund a payment

Returns funds to the payer. Omit amount to refund the full unrefunded remainder of the payment.

Partial refunds may be issued repeatedly until the sum of all succeeded refunds equals the payment amount. A request that would exceed that total is rejected with 422 and refund_amount_exceeded; the check is performed against settled totals, so a refund issued while another is still processing may be rejected even though arithmetic on the payment object alone suggests headroom.

Refunding the full amount of the only payment on an invoice does not reopen the invoice. Its state remains paid.

Idempotency-Key
required
string [ 16 .. 255 ] characters
Example: 8f14e45f-ea1b-4c2d-9a35-7b1d6e0c3a92

A client-generated unique key that makes this POST safe to retry. Use a UUIDv4 or another value with at least 128 bits of entropy, and generate it once per logical operation, not once per HTTP attempt.

Semantics:

  • First use. The request is processed and the response is stored against the key for 24 hours.
  • Replay with an identical body. The stored response is returned verbatim, with the original status code and an Idempotent-Replay: true header. No new resource is created.
  • Replay while the original is still in flight. 409 with the idempotency_in_progress error code. Retry after a short delay.
  • Reuse with a different body. 409 with idempotency_key_reused. Nothing is processed. This is a bug in the caller: the same key is being used for two different operations.
  • After 24 hours. The key is forgotten and a request bearing it is treated as new. An integration that retries on a schedule longer than 24 hours must not rely on this header for deduplication.

The key is scoped to the account and the endpoint. The same key may be used on createInvoice and on createPayment without collision.
